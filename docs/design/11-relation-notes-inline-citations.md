## 1. 背景（2026-11-13）

用户在检查 2.1 的判断写法时提出：

1. 一条判断要能**原子化验证、单独复现**。判断里用到的量和术语（例如"收敛"指"损失与最终值之差小于 0.01 的最早轮数"）如果没有在正文展开，也没有引用定义它的原文段落，别人无法核对。
2. 关系现在只有"依据了"，**看不出为什么引用这一段**。每条关系都应能说明原因，而不只是依据关系。
3. 框架页那种行内引用（引用写在句子里）是合理的；可以与关系行并用。

### 1.1 现状（代码所得）

- 判断存两样东西：正文 `text`（纯文本）与关系行（`cites`、`supports` 等，主语是这一版判断）。关系的 `qualifiers` 目前只有 `condition`、`reason`（写 `relations` 时可给）和 `cites` 自动带的段落指纹 `sha256`、`unit`。
- 正文里写 `[[ID]]` 或 `[[ID|文字]]` 时，`judgments._prepare` 会用 `extract_refs` 把它**自动并入 `cites`**（沿用框架页的写法）。但它不带说明，也不指出"哪句话对应哪条"。
- 改写判断（`revise`）沿用上一版的 `cites` 时，只取了对端引用，**不带 `qualifiers`**：如果以后 `qualifiers` 里有说明，改写会把它们丢掉。2.1.1 新增的人改关系（`entry.relate` → `VersionService.change_relations`）也一样：它把当前版的 `cites` 取成引用字符串再交给 `revise`，新加的关系只认 `condition`、`reason`；且正文里的 `[[…]]` 依据不能被它去掉（要改正文）。
- 检索索引里判断的正文就是 `text`。

## 2. 原则

1. **关系行仍是唯一的事实来源。** 正文里的 `[^n]` 只是指向关系行的编号，不重复存放对端、段落或说明。
2. **每条关系可以有说明，写不写由写的人定。** 系统不拒绝、不为"没写说明"报错；写作原则放在 Skill 里，系统只提供位置、提示和显示。
3. **词表只做提示和建议。** `role`（作用）是自由文本，词表里的名字只是候选；真正重要的写作原则在 Skill 中说明。
4. **写入不依赖解析正文来"猜"。** 行内标记与关系的对应关系是写入时的参数，系统只检查两边是否一致。
5. **不扩大不变式的影响**：账本仍只追加；关系仍固定到对端的某一版；说明与标记不参与地位、现状的推出（它们不是依据，也不改变依据来源）。

## 3. 决定

### A. 每条关系可带说明

| 编号 | 决定 | 理由 |
|---|---|---|
| D-01 | **所有关系都可以带 `why`（原因，一句话）与 `role`（作用，自由文本）**，存在关系的 `qualifiers` 里，不改表：`cites`、`supports`、`opposes`、`answers`、`targets`、`coexists_under`、`relates` 都一样。`why` 回答"为什么连这一条"，例如"这里定义了 `epochs_to_within_0.01`：损失与最终值之差小于 0.01 的最早轮数"。原有的 `reason` 并入 `why`（旧数据没有，不需迁移）。`condition` 保持原样（`coexists_under` 必须写）。系统自动写的关系（晋升事实记录写的 `cites`、`produced`、`consumed`）不带 `why`，界面显示为空 | 每条关系都要有说明，位置统一 |
| D-02 | **`role` 只给提示，不做校验。** 词表 `core/vocab.py` 为每个谓词列出建议的作用名（`ROLE_HINTS`），随 `vocab.get`、MCP 提示、前端输入候选一起给出，AI 与人可以直接用，也可以自己写：<br>`cites`：定义、方法、数据、条件、直接依据、背景；<br>`supports`：数值一致、方法不同但结论一致、条件更宽；<br>`opposes`：数值冲突、条件不同、方法不同；<br>`answers`、`targets`、`coexists_under`、`relates`：不给建议。<br>真正的撰写原则（什么时候该写定义、原因写到什么程度）写在 Skill 里（D-11 至 D-14） | 词表是提示，原则在 Skill |
| D-03 | **写入形式**：`judgment.write` 的 `cites` 每项可以是引用字符串（沿用），或 `{ref, why?, role?, marker?}`；`relations` 每项增加 `why`、`role`、`marker`。两种写法可以混用。`revise` 沿用上一版的关系时**连同 `qualifiers`（说明与标记）一起沿用**；`cites` 给出新值时整体替换依据，已有说明不会自动搬到新引用上（要保留就在新值里再写）。人改关系（`entry.relate`）同样沿用未被去掉的关系的说明，新加的关系 `add` 每项也接受 `why`、`role`、`marker`（`marker` 与同一次更正里的正文一起校验，对不上拒绝） | 改写不丢说明；行为可预测 |
| D-04 | **`why`、`role` 只是写法提示，不是必填项；系统不因没写而拒绝或提示。** Skill 说明它们用来讲清"这条关系对应判断里的哪一点、起什么作用"。巡检（设计稿 08）统计"关系没有说明"的比例，供人决定要不要加强，不在写入时打扰 AI | 用户决定："原因可以不说明"，why 与 role 都是提示 |

### B. 行内引用 `[^n]`

| 编号 | 决定 | 理由 |
|---|---|---|
| D-05 | **标记写法 `[^n]`**（n 是 1–3 位数字，如 `[^1]`），写在要说明的那句话后面。同一个标记可以对应**多条**关系（一句话同时引用两个段落），一条关系至多带一个标记。标记编号只在这一版判断内有意义；改写后允许重新编号 | 短，与正文里别的方括号不混淆；沿用 Markdown 脚注的习惯写法 |
| D-06 | **标记与关系的对应存在关系上**：`qualifiers.marker = "1"`。正文里没有脚注内容，只有 `[^1]`；对端、段落、说明都从关系行读。展示时 `[^1]` 渲染成上标，悬停或点开显示对应关系的对端（段落原文）、作用与原因 | 唯一事实来源是关系行 |
| D-07 | **写入时的一致性检查**（先校验、再写入，不一致整条拒绝，`INVALID_ARGUMENT` 并指出是哪个标记）：<br>① 正文里每个 `[^n]` 至少对应这一版的一条带 `marker=n` 的关系；<br>② 每条带 `marker` 的关系，它的标记必须出现在正文里。<br>`revise` 同样检查：改了正文却没改关系（或反过来）会被拒绝，避免正文与依据悄悄脱节。没有标记的判断照常写入（不要求每条关系都对应一个标记） | 防止悬空标记；老写法不受影响 |
| D-08 | **与 `[[ID]]` 的关系（用户决定：保留，但不建议）**：框架页的 `[[ID]]` 写法与判断里已有的"正文里的 `[[ID]]` 自动并入 `cites`"保持不变，不拆除。但它不带说明、也不指出哪句话对应哪条，所以 Skill **推荐正文里用 `[^n]`，不建议用 `[[ID]]`**；`[[ID]]` 只在想"提到"某个条目时用，当依据时仍用 `cites` 补说明。同时 Skill 要求：正文和条件里能抽出的关系（用到的依据、佐证、反驳、对象）都要建立成关系（D-14）。两者不冲突：同一个对端被两种方式写到时，只存一条关系；这条关系若同时带了 `[^n]` 的说明，说明归在这条关系上。人改关系时，仍不能去掉正文里 `[[…]]` 写的依据（2.1.1 已有的规则） | 兼容已有行为，不引入两套规则 |
| D-09 | **索引不含标记**：判断正文进入全文索引与向量单元前，去掉 `[^n]`；检索结果里的 `text` 与 `snippet` 同样去掉；`entry_get` 返回的 `text` 保留标记（前端据此渲染）。标记不进入标题、摘要、`preview`、`status_note` | 用户决定 |
| D-10 | **被引方感知（双向）**：设计稿 10 D-10 已规定每条关系从两端都查得到。被引条目的关系里"被引"那一栏（入边）由关系表按宾语查出，**不写新行、不产生被引条目的新版本**，所以被引不影响被引文件的版本；它用于联想搜索、建图，以及原件变化时找出受影响的判断。入边同样带 `why`、`role`、`marker`。<br>**返回给 AI**：`entry_get` 的每条关系带 `why`、`role`、`marker`；检索结果的 `links` 仍是 `{p, ref}`，不带说明（保持简短，AI 需要时用 `entry_get`）。`judgment.write` 的返回里列出本次写入的标记与它们对应的关系数 | 检索结果仍然只报例外 |

### C. 写判断的撰写原则（Skill）

这是写在 Skill 里的原则，系统不强制：

| 编号 | 决定 | 理由 |
|---|---|---|
| D-11 | **写判断的三条规则：有价值**（对后续理解、决策或复用有意义，沿用现有规则）**、原子化即可复现**（只凭这一条就知道做了什么、得到什么结论，精确到别人能照着重做、重算或重新核对；不是"拆成多条"）**、不带框架性措辞**（沿用现有规则）。过程判断放宽后两条：提问、尝试、停下的路线可以不满足原子化与可复现，但仍要写清对象和条件 | 用户确认的写入规范 |
| D-12 | **正文里的专有量和术语必须展开，并引用定义它们的原文段落**：用 `cites` 项 `{ref: "art_…#段落", role: "定义", why: "…"}`，正文在对应处写 `[^n]`。展开写在正文，不依赖读者去查 | "收敛""最终值"这类量没有定义就无法验证 |
| D-13 | **模糊但有价值的判断允许写，但要把条件写清楚，并加一个 flag**：`conditions` 里分别写明**哪些使用条件已经清楚、哪些还不清楚**（如"已知：逻辑回归，α=0.001，批量 128；不清楚：更大学习率、其他数据集"）。同时写入时用参数 `scope_unclear=true` 声明"适用范围尚不清晰，不能过于相信"。这个 flag 是判断的一个**显式字段**（和 `conditions`、`external_author` 一样，由写的人在写入时决定），**系统不根据 `conditions` 的写法去推**。字段为真时，条目页与检索结果的说明里显示"适用范围未明"（说明标记 `scope_unclear` 直接取自这个字段），读的人把它当线索使用。不写（默认假）是常态。人更正判断时可以改这个字段 | 用户决定：要求 AI 写入时就决定，不靠写法推断；与"条件没写"（`conditions_unstated`）区分：那是漏写，这是写了、并且声明有不清楚的部分 |
| D-14 | **正文和条件里能抽出的关系都要建立成关系，说明（`why`、`role`）是写法提示**：用到的原件段落、事实记录、别的判断写成 `cites`；佐证、反驳、回答、针对、条件并存写 `relations`；对象填 `objects`；条件来自某份材料时也引用那一段（作用"条件"）。`cites` 的每一项都对应一条关系；正文里的引用用 `[^n]`，每个 `[^n]` 有关系对应（D-07）。建立关系是双向的：被引条目的关系里出现反向的"被引"，不改变被引条目的版本（实现见 D-10）。不写说明不报错（D-04） | 用户确认 |

### D. 界面

| 编号 | 决定 | 理由 |
|---|---|---|
| D-15 | **条目页**：判断正文里的 `[^n]` 渲染成上标，点开（或悬停）显示"作用 · 原因"与对端段落原文；关系区每一行在对端标题后显示 `role`（小标签）与 `why`（一行小字），没有就不显示。关系区行内标注它在正文里的位置（"对应 [^1]"） | 正文与关系区互相对得上 |
| D-16 | **写判断的界面**（工作台）：每条依据带两个可选输入（作用、原因），作用有候选；正文里输入 `[^` 时提示可选的标记 | 人也能写出同样的结构 |
| D-17 | **关系图**不变；节点详情的关系列表同条目页 | 图保持简洁 |

### E. 人工更正：关键字段在工作台里方便地改（与 2.1.1 的"人改关系"同一目标）

现状（2.1.1）：人在工作台能改判断的**正文与依据**（`entry.correct`），能单独增删**关系**（`entry.relate`）；但判断的**条件、对象、类型、原作者、重开条件**，原件的**标题、依据来源档次、说明字段**都没有入口，只能靠改正文绕开，或写一条新判断。AI 写错了一个条件，人就得重写整条。

| 编号 | 决定 | 理由 |
|---|---|---|
| D-18 | **一次更正 = 一个新版本，所有关键字段一起改**：工作台的"更正"面板里，人可以同时改正文、关键字段与关系，写一次理由，只产生一个新版本（不为正文、字段、关系分别写版本）。可改的关键字段：<br>**判断**：类型（结论 / 过程 / 规定）、正文、`conditions`、`scope_unclear`、对象、原作者（`external_author`）、重开条件（过程）、`local_observation`（人勾选）、依据与关系（增删，带 `why`、`role`；`marker` 随正文一起改）。<br>**原件**：标题、依据来源与档次、说明字段（`metadata`，按键覆盖）、对象；内容变了仍是登记新版本。<br>**过程日志、事实记录、读取记录**：只改正文，保持现状。它们的条件、方法、边界属于"当时记下了什么"，不开放（条件只能整理、不能补写，设计稿 07） | 关键字段错了不必重写整条；一次改动一个版本，历史清楚 |
| D-19 | **后端**：`entry.correct`（仅人）扩展为通用更正：除 `text`、`path`、`cites` 外，接受 `kind`、`conditions`、`scope_unclear`、`objects`、`external_author`、`reopen_condition`、`local_observation`、`relations_add`、`relations_remove`（含 `why`、`role`）、`title`、`external_tier`、`source_class`、`metadata`；没给的字段沿用上一版，至少改一项，理由必填。`entry.relate` 保留（只改关系的快捷入口），内部与 `entry.correct` 走同一个服务函数。校验：类型改为过程时，若已有结论把它当依据，拒绝并指出是哪几条（不变式 I11）；`[^n]` 与关系的一致性检查（D-07）；去掉依据时不能去掉正文里 `[[…]]` 写的（2.1.1 规则）。版本历史的 `changes` 列出这一版改了哪些字段与关系，供界面显示 | 一个入口；不破坏已有的约束 |
| D-20 | **界面**：条目页"更正"面板按分区编辑，**预填当前值**，只提交改动的项：①正文与关键字段（条件、`scope_unclear` 勾选、对象、原作者、类型等，按条目种类显示）；②依据与关系（沿用 `RelationEditor` 的列表与 `EntryPicker`，每条加"作用""原因"输入，并显示它对应的 `[^n]`）；③理由；④写入前显示"这一版将改动：……"的变更摘要（字段前后对比、增删的关系）。正文里 `[^n]` 与关系不一致时，在提交前即时提示。快捷键与现有编辑一致。"写判断"表单与"更正"面板共用同一个判断表单组件，字段一致 | 人能快速改；不用在三个地方各改一次；和写入时的字段一致 |
| D-21 | **权限不变**：更正、改关系仍只能由人做（`effect=user`），不进 MCP；AI 仍只能用 `revises` 改写自己会话写的判断（`revise` 的参数同样包含上述判断字段）；别人的判断写 `opposes` | 不变式 4 |

## 4. 对不变式的影响

| 不变式 | 影响 |
|---|---|
| I1 账本只追加 | 不变；说明与标记写在关系的 `qualifiers`，随关系一起追加 |
| I2 框架不能作为依据 | 不变；说明、标记、`[[ID]]` 都不改变"哪些关系算依据" |
| I3 坐标由系统推出 | 不变；`scope_unclear` 是写的人在写入时声明的内容字段（与 `conditions`、`external_author` 同类，不是坐标）；说明里显示的"适用范围未明"直接取自这个字段，不另行推断。AI 可以设置，不涉及只有人能标的本地实证 |
| I5 / I8 落盘格式只增不改 | 不变；不改表，格式号仍为 2。旧数据没有说明和标记，照常显示 |
| I7 引用固定版本 | 不变；标记不影响关系两端固定到版本 |

## 6. 不采用

| 方案 | 不采用的原因 |
|---|---|
| 在正文里写脚注内容（`[^1]: …`） | 对端、段落、说明会存两处，改写时容易不同步；改为只在关系行里存，正文只放编号 |
| 行内直接写 `[[art_…#p3]]` 作为主要写法 | 长 ID 塞进正文，影响可读性与索引；也没有"作用、原因"的位置；仅保留它作为"提到别的条目"的写法 |
| 把关系说明作为必填并拒绝不写的 | 用户决定可以不写；强制会让 AI 为通过而写套话 |
| 写入时对"没写说明"给提示 | 用户决定不需要；改为巡检统计 |
| `role` 用封闭词表并校验 | 词表只是提示，自由文本更能表达具体情况；约束靠 Skill |
| 系统检查"术语是否已定义" | 机器看不出一个词是否定义清楚；只能靠 Skill 与巡检、复核 |
| 从 `conditions` 的固定开头自动推出 `scope_unclear` | 用户决定：要求 AI 写入时自己决定，不靠系统按写法推断；改为显式布尔字段 |
| 标记进入检索索引 | 用户决定不需要；会成为噪声 |
| 检索结果的 `links` 带说明 | 会把每条结果撑长；需要时用 `entry_get` |
